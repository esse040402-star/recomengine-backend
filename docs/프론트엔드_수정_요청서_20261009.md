## 1. 수정 요청: 제외 요소를 고르면 추천이 0건이 됨 (높음)

### 증상
설문에서 아래 선택지를 고르면 `recommend()`가 빈 목록을 돌려주고, 화면에는 "지금 조건에 맞는 게임이 없어요."가 나옵니다. 오류는 아니고 의도된 보수적 제외(명세서 BR-06)이지만, **고를 수 있는 선택지 대부분이 사실상 결과를 없애는 상태**입니다.

### 원인
`frontend/src/services/preferenceEngine.js:130`의 필터입니다.

```js
(!p.lowSpec || g.lowSpec === true)
&& !p.avoid.some(a =>
     g.risks.includes(a)
  || (a === 'monetization' && !g.riskCoverage?.includes(a))
  || (g.classification === 'steam-derived' && !g.riskCoverage?.includes(a)))
```

- 카탈로그(`frontend/src/data/generated/catalog.json`)에 `lowSpec: true`인 게임이 **0개**입니다.
- `riskCoverage`(위험 정보를 확인했다는 표시)는 Steam 파생 게임 122개(출시 예정 1개 포함)에 `pvp`, `mature` 두 가지만 있습니다. 큐레이션 15개에는 `riskCoverage`가 아예 없습니다.
- 그래서 `pvp`·`mature` 이외의 제외 요소를 고르면 Steam 파생 게임이 전부 빠지고 큐레이션 15개만 남습니다.

### 제외 요소를 **하나만** 골랐을 때 남는 후보 수
(기기 조건 없음, 출시 예정 1개 제외한 후보 136개 기준. 카탈로그 JSON으로 같은 규칙을 계산한 값입니다.)

| 제외 요소 (코드) | 선택지 문구 | 남는 후보 |
|---|---|---|
| 과금·광고 유도 (`monetization`) | "🚫 P2W 및 과도한 BM(가챠/현질) 유도", "🚫 [과금/광고 피로] …" | **0개** |
| 높은 난이도 (`difficulty`) | | 7개 |
| 강한 섬광 (`flash`) | | 8개 |
| 시간 압박 (`pressure`) | | 8개 |
| 복잡한 규칙 (`complex`) | | 9개 |
| 카메라 멀미 (`motion`) | | 10개 |
| 반복 작업 (`grind`) | | 12개 |
| 긴 대사·텍스트 (`text`) | | 13개 |
| 공포·기괴한 연출 (`horror`) | | 13개 |
| 대인 경쟁 (`pvp`) | | 98개 |
| 성인 소재 (`mature`) | | 114개 |
| 저사양 선택 (`lowSpec`) | 비게이머 Q1 "일반 사무용 컴퓨터 / 노트북 (사양 낮은 가벼운 게임)" (`preferenceEngine.js:35`) | **0개** |

여러 개를 함께 고르면 더 줄어듭니다. 기기 조건까지 겹치면 0건이 되기 쉽습니다.

### 제안 (팀에서 하나를 정해 주세요)
| 방식 | 내용 | 장단점 |
|---|---|---|
| A. 데이터 채우기 | 게임마다 `lowSpec`, `riskCoverage`를 채움 (Steam 태그·사양 정보로 추정 가능) | 규칙(BR-06)은 그대로. 작업량이 가장 큼 |
| B. 규칙 완화 | "미확인 = 제외"가 아니라 "미확인 = 후순위 + 안내 문구"로 변경 | 결과가 비지 않음. 명세서 BR-06을 고쳐야 함 |
| C. 선택지 정리 | 데이터가 없는 항목(저사양, 과금)은 당분간 선택지에서 숨기거나 "준비 중" 표시 | 가장 빠름. 기능이 줄어듦 |

### 재현 방법
"게이머가 아직 낯설어요"(비게이머)로 시작해 빠른 설문 Q1에서 "일반 사무용 컴퓨터 / 노트북"을 고르고 설문을 끝내면, 결과 화면에 추천 카드 대신 "조건에 맞는 게임이 없어요"가 나옵니다(위 규칙을 코드로 계산한 결과이며, 화면에서 직접 눌러 확인한 것은 아닙니다). 화면 문구는 `frontend/src/components/game/GameCard.jsx:15`에 있습니다.

## 2. 확인 요청: "이 브라우저에만 저장" 문구 (중간)

스토리보드 24·26·27쪽에도 같은 문구가 있어서 **설계에 있는 문구**입니다. 다만 지금은 로그인하면 서버(`/api/account/state`)에 저장되므로, 로그인 상태에서는 사실과 다릅니다.

| 위치 | 현재 문구 | 제안 |
|---|---|---|
| `components/common/DialogContents.jsx:29` (평가 작성) | "{이름} 이름으로 이 브라우저에만 저장됩니다." | 로그인: "내 계정에 저장됩니다." / 게스트: 현재 문구 |
| `components/common/DialogContents.jsx:44` (피드백) | "선택 즉시 이 브라우저의 추천 엔진에 저장됩니다. …" | 로그인이면 "내 계정에 저장됩니다"로 분기 |
| `components/game/Reviews.jsx:5` | "이 브라우저에 저장됨", "직접 작성한 평가는 이 브라우저에 저장됩니다." | 같음 |

`DialogContents.jsx:47`(로그인·가입 안내)은 서버 연결 여부로 이미 문구를 나눠 놓았습니다. 같은 방식을 쓰면 됩니다.

참고로 `ProfilePage.jsx:21`의 "프로토타입 테스트"도 스토리보드 30쪽에 같은 이름으로 있습니다. 버그는 아니고, 정식 서비스로 가기 전에 이름을 정하면 됩니다.

## 3. 확인 요청: 로그인 시 빈 상태로 시작 (낮음)

`frontend/src/state/AppContext.jsx:38`, `:68`에서 서버에 저장된 상태가 없는 계정으로 **로그인**하면 빈 상태로 시작하고, 게스트 상태 이관은 **회원가입 때만** 합니다. 다른 사람의 게스트 정보가 기존 계정에 섞이지 않게 한 의도된 동작이며 변경 내역 문서에도 적혀 있습니다.

다만 게스트로 설문을 풀다가 기존 계정으로 로그인하면 그 답변이 조용히 사라집니다. 로그인 직전에 "이 기기의 답변은 가져오지 않아요" 같은 안내를 넣을지 검토해 주세요.

## 4. 알고 있는 한계 (문서에 이미 있음, 참고용)

- 가입은 "가입 → 상태 저장" 두 요청이라 한 번에 처리되지 않습니다. 저장이 실패하면 "미전송 복구본"으로 다시 저장하는 흐름이 이미 있습니다.
- 여러 기기에서 쓰면 마지막 저장이 이깁니다. 서버가 버전을 돌려주지 않기 때문입니다(명세서 BR-25의 낙관적 잠금은 미구현).
- 추천 점수는 프론트가 계산합니다. 서버 재계산은 `/api/v1` 구현 단계에서 합니다.

## 5. 서버 쪽에서 맞춰 둔 것 (프론트가 알아야 할 값)

| 항목 | 값 |
|---|---|
| 서버가 받는 호출 | `/api/account/{session,signup,login,logout}`, `PUT /api/account/state`, `/api/status`, `/api/market`, `/api/steam/{reviews,details}`, `/api/survey/generate` |
| 오류 응답 | `{"error": "화면에 보여줄 한국어 메시지", "detail": ...}`. 프론트 `transport.js`가 `error`·`message` 둘 다 읽으므로 그대로 사용 가능 |
| 저장 상태 크기 | `PUT /api/account/state`는 **1MB 이하**. 넘으면 413 |
| 로그인 시도 제한 | 연속 실패 시 429 "로그인 시도가 너무 많아요…" |
| AI 문항 | `source: "ollama"`로 응답하고 `blueprint`는 28문항 필수. 서버 제한 50초(프론트 55초보다 먼저 끝남), 실제 15~22초. `applyAI`는 제목이 **하나라도 중복이면 응답 전체를 버리는데**, 서버가 AI 제목이 다른 문항의 원래 제목과 겹치지 않게 보정하도록 2026-10-09에 고쳤습니다(고치기 전에는 화면이 항상 "AI 연결 없이"로 표시됨). 프론트는 변경 없음 |
| 스팀 인기 순위 | 2026-10-09 한동안 스팀 차트 주소 자체가 500을 내서 `새로 불러오기`가 실패했지만(서버 502), 같은 날 복구되어 지금은 실시간 순위가 정상으로 표시됩니다. 스팀이 다시 오류를 내면 화면은 저장된 자료를 유지하고 서버의 한국어 오류 메시지를 토스트로 보여 줍니다(`usePageController.jsx`의 `refresh-market`). 프론트 수정은 필요 없습니다 |
| 이미지 | 서버 중계 API는 없습니다. 프론트가 `steamMediaURL`로 스팀 이미지 주소를 직접 쓰는 현재 방식이 서버와 맞습니다 |
| 개발 실행 | Vite 프록시(`/api` → `127.0.0.1:8000`)로 같은 주소처럼 동작하므로 쿠키 로그인이 됩니다 |
| 다른 주소로 서버를 지정할 때 | `VITE_API_BASE_URL`을 쓰면 서버 `CORS_ORIGINS`에 프론트 주소(예: `http://localhost:5173`)를 추가해야 합니다. 기본값에는 `8000`만 있습니다 |

### 확인한 응답 필드 (프론트가 읽는 값 = 서버가 주는 값)
- 리뷰: `id, text, truncated, positive, created, language, hours, helpful, purchased, receivedFree, url`, 그리고 `cursor`, `checkedAt`
- 계정: `user.id`, `user.name`, `state`
- 시장: `{section, updatedAt, data}`, 가격은 최소 화폐 단위(`6480000` = 64,800원)

## 6. 확인하지 못한 것

- `npm ci`, `npm test`, `npm run build`, 브라우저 테스트는 **실행하지 않았습니다.** 문서에 적힌 프론트 테스트 8개·브라우저 검증 결과는 제가 재현한 값이 아닙니다.
- 실제 화면에서 눌러 보며 확인한 것이 아니라, 코드와 데이터 파일을 읽고 계산한 결과입니다. 1번 표의 숫자는 `catalog.json`과 `preferenceEngine.js:130`의 규칙을 그대로 적용한 값입니다.
- 실제 Supabase 쓰기·로그인은 아직 해 보지 않았습니다. 지금 서버 테스트는 가짜 DB 기준입니다.
