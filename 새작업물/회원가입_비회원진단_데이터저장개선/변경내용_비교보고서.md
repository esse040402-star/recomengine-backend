# 회원가입 및 비회원 진단 데이터 저장 기능 업데이트 비교 보고서

## 1. 비교 기준

제공된 두 ZIP의 프로젝트 파일을 비교했습니다.

- 원본: `recomengine-backend-main/`
- 업데이트: `recomengine_auth_flow_fixed/recomengine update ver.1/recom_project/`
- 비교 범위: 소스 코드, 설정, 문서 파일
- 제외 범위: `.venv/`, `node_modules/`, `__pycache__/`, `.pytest_cache/` 등 생성물 및 설치된 의존성

비교 결과 공통 파일 139개 중 **17개 파일의 내용이 변경**되었고, 이 비교 범위에서는 추가·삭제된 소스 파일이 없었습니다. `requirements.txt`, `frontend/package.json`, 루트 `.env.example`은 두 ZIP에서 내용이 동일했습니다. 따라서 의존성 목록이나 환경변수 이름이 새로 추가된 것은 아닙니다.

## 2. 핵심 변경 내용

### 2.1 회원가입·이메일 인증·로그인

관련 파일:
- `app/routers/account.py`
- `app/services/accounts.py`
- `frontend/src/hooks/profileActions.js`
- `frontend/src/state/AppContext.jsx`
- `frontend/src/App.jsx`
- `frontend/src/components/common/DialogContents.jsx`

변경 사항:
1. 회원가입 처리에서 Supabase Auth로 기존 이메일/비밀번호 로그인 가능 여부를 먼저 확인한 뒤, 필요하면 신규 가입을 시도하도록 변경했습니다.
2. 이메일 인증이 필요한 경우 서버가 `email_confirmation_required` 응답을 반환하고, 인증이 끝나기 전에는 로그인 세션을 발급하지 않도록 처리했습니다.
3. 프론트엔드는 인증 메일 안내 상태를 구분하고, 비밀번호 확인값을 검사합니다. 비밀번호 자체는 인증용 임시 정보로 저장하지 않습니다.
4. 인증 완료 후 돌아오는 Supabase 링크의 토큰/코드 형식을 확인해 인증 완료 안내 화면을 표시하도록 보완했습니다.
5. 회원가입 성공 후에는 게임 이용 경험 선택 화면(`track-select`)으로, 일반 로그인 성공 후에는 메인 화면으로 이동하도록 흐름을 구분했습니다.
6. 계정 생성·로그인 실패, 중복 이메일, 이메일 미인증 등의 응답을 사용자에게 안내할 수 있도록 처리했습니다.

### 2.2 비회원 및 회원 데이터 저장

관련 파일:
- `frontend/src/state/AppContext.jsx`
- `frontend/src/utils/storage.js`
- `frontend/src/hooks/profileActions.js`
- `app/routers/account.py`
- `app/services/accounts.py`

변경 사항:
1. 비회원 상태는 브라우저 로컬 저장소에 저장하며, 저장 시각 기준 7일이 지나면 만료 데이터로 처리합니다.
2. 저장 형식에 저장 시각과 상태 데이터를 함께 기록하고, 형식이 맞지 않거나 만료된 데이터는 초기 상태로 처리합니다.
3. 로그인 사용자의 상태는 사용자 ID별 저장 키로 분리해 게스트 데이터와 섞이지 않도록 합니다.
4. 회원 상태 변경은 저장 큐를 통해 서버에 비동기 저장하고, 전송 중인 변경사항이 있을 때 페이지 이탈을 경고하도록 처리합니다.
5. 서버 저장 실패 시 미전송 상태를 로컬에 보관하고 복구/재시도 흐름을 제공합니다.
6. 회원가입 또는 로그인 후 서버에서 기존 계정 상태를 조회해 프론트 상태에 반영합니다.

계정 API:
- `GET /api/account/session`: 현재 로그인 세션과 계정 저장 상태 조회
- `POST /api/account/signup`: 회원가입 및 이메일 인증 필요 여부 반환
- `POST /api/account/login`: 로그인 및 계정 저장 상태 조회
- `POST /api/account/logout`: 세션 쿠키 삭제
- `PUT /api/account/state`: 로그인 사용자의 상태 저장

서버 상태 저장은 Supabase의 `user_states` 테이블을 사용합니다. 테이블, 고유 제약, RLS/권한은 실제 Supabase 프로젝트에서 별도로 확인해야 합니다.

### 2.3 진단 설문 결과 저장

관련 파일:
- `frontend/src/hooks/surveyActions.js`
- `frontend/src/services/recommendationService.js`
- `app/routers/survey.py`

변경 사항:
1. 설문 완료 시 완료된 빠른 설문·심화 설문·취향 설문의 답변을 모읍니다.
2. `POST /api/sessions`로 진단 세션을 만들고, 답변이 있으면 `PUT /api/sessions/{session_id}/answers`로 저장합니다.
3. 분석 축, 제목, 취향 정보, 근거를 `POST /api/sessions/{session_id}/complete`로 전달합니다.
4. 결과 화면 이동을 서버 저장 완료까지 막지 않고 백그라운드에서 저장합니다.
5. 저장에 실패하면 추천 화면은 유지하면서 서버 저장 실패 안내를 표시합니다.
6. 기존 심화 설문 생성 API에 더해 `GET /api/survey/questions?track={track}&stage={stage}` 조회 경로가 추가되었습니다. 해당 경로는 Supabase의 `survey_questions` 테이블을 조회합니다.

### 2.4 비회원 시작 및 화면 이동

관련 파일:
- `frontend/src/App.jsx`
- `frontend/src/hooks/usePageController.jsx`
- `frontend/src/pages/WelcomePage.jsx`
- `frontend/src/utils/routes.js`
- `frontend/src/components/layout/AppLayout.jsx`
- `frontend/src/components/common/Modal.jsx`
- `frontend/src/styles/prototype.css`

변경 사항:
1. 시작 화면에서 비회원 시작 경로를 추가하고 이용 경험 선택 화면으로 연결합니다.
2. 비회원도 이용 경험을 선택하고 빠른 진단을 완료하면 메인 기능으로 진입할 수 있도록 경로 검사를 조정했습니다.
3. 회원가입 완료 후 이용 경험 선택, 로그인 완료 후 메인 화면으로 이동하는 흐름을 분리했습니다.
4. 이메일 인증 완료 안내와 관련 모달/레이아웃 표시를 보완했습니다.

## 4. 설정 및 의존성 비교

- `requirements.txt`: 원본과 업데이트 파일의 내용이 동일합니다.
- `frontend/package.json`: 원본과 업데이트 파일의 내용이 동일합니다.
- 루트 `.env.example`: 원본과 업데이트 파일의 내용이 동일합니다. 기존에 Supabase, 세션, 게임 API, Ollama 설정 항목이 이미 포함되어 있어 새 변수 추가는 확인되지 않았습니다.
- 업데이트 ZIP에는 별도의 `frontend/.env.example`도 포함되어 있습니다. 이 파일은 Vite 개발 서버의 API 프록시 주소와 API 사용 여부를 위한 예시이며, 루트 백엔드 환경변수 파일과 용도가 다릅니다.

루트 `.env.example`의 실제 비밀값은 비워 두어야 합니다. 실제 `.env`, Supabase service role 키, 세션 비밀값 및 외부 API 키는 저장소에 커밋하지 마세요.

## 5. 실행 및 검증 시 확인할 항목

1. Supabase Auth의 이메일 인증 활성화 여부, 인증 메일 링크 및 리디렉션 URL
2. 실제 DB 모드에서 `SUPABASE_URL`, `SUPABASE_SERVICE_KEY`, `SUPABASE_ANON_KEY`, `SESSION_SECRET` 설정 여부
3. `user_states` 테이블, `user_id` 고유 제약, upsert 권한 및 RLS 정책
4. 진단 세션·응답·완료 API가 사용하는 테이블과 정책
5. 설문 문항 조회용 `survey_questions` 테이블과 `track`, `stage`, `question_no` 컬럼
6. 브라우저 쿠키의 SameSite/Secure 설정과 프론트·백엔드 origin/CORS 설정
7. 비회원 7일 저장, 회원별 상태 분리, 저장 실패 후 복구, 이메일 인증 전후 흐름

## 6. 테스트 상태 및 한계

이 보고서는 제공된 원본 ZIP과 업데이트 ZIP의 파일 비교를 바탕으로 작성했습니다. **이번 문서 작성 과정에서 실제 Supabase 계정/DB, 이메일 발송, Ollama 서버를 연결한 통합 테스트는 수행하지 않았습니다.** 따라서 코드에 구현된 동작 설명과 실제 외부 서비스 환경에서 검증된 동작을 구분해야 합니다.

로컬 검증은 프로젝트 루트에서 백엔드 테스트(`pytest -q`), 프론트엔드 테스트(`npm test`) 및 빌드(`npm run build`)를 실행하고, 별도로 Supabase 이메일 인증과 저장 테이블을 확인하는 방식으로 진행하세요.
